# ИИ-консультант Store — хакатон ИИкузница

Агент поддержки для store.softline.ru: подбирает ПО по каталогу Store, сверяет лицензии,
отвечает по базе знаний, готовит КП и передаёт сложные случаи менеджеру.

```
support-assistant/
├── Dockerfile          ← единый образ: сервер на Go + собранный фронтенд (его собирает Railway)
├── docker-compose.yml  ← запуск локально, режим разработки, пересборка каталога
├── railway.json        ← настройки деплоя на Railway
├── backend/            ← сервер на Go: API, WebSocket, агент; все данные — в Postgres
├── frontend/           ← React-приложение (витрина, чат, кабинет менеджера)
└── data/               ← скрипты: каталог из фида и выжимка из переписок → backend/data/
```

### Сервер на Go (`backend/`)

| Где | Что |
| --- | --- |
| `main.go` | запуск: настройки из переменных окружения, загрузка каталога, подключение к Postgres |
| `internal/agent/bot.go` | **агент**: распознаёт, что хочет клиент, задаёт уточняющие вопросы, передаёт менеджеру (`GenerateReply`) |
| `internal/agent/catalog.go` | каталог из фида: поиск продукта по фразе, расчёт цены под количество и срок, редакции, российские аналоги |
| `internal/agent/offers.go` | варианты решения с обоснованием, сравнение, позиции КП |
| `internal/agent/kb.go` | база знаний: ответы о доставке, оплате, НДС, документах |
| `internal/agent/seed.go` | демо-обращения из реальных переписок |
| `internal/service/` | диалоги, передача менеджеру, КП, статистика (`service.go`); запросы к таблицам обращений (`repo.go`) |
| `internal/db/` | подключение к Postgres и схема всех таблиц |
| `internal/server/` | HTTP-маршруты (`server.go`), вход и сотрудники в Postgres (`auth.go`), WebSocket (`hub.go`) |
| `internal/model/types.go` | формат данных API — совпадает с `frontend/src/api/types.ts` |
| `data/` | каталог Store из фида (`catalog.json.gz`, 6 000 продуктов) и выжимка из переписок (`chats.json`) |

Тесты агента — сверка с эталонными ответами на 77 диалогов из реальных переписок (`backend/testdata`):

```bash
cd backend && go test ./...
```

## Запуск в Docker

```bash
docker compose up --build
```

- http://localhost:8080 — витрина Store с виджетом консультанта
- http://localhost:8080/operator — кабинет менеджера (обращения, КП, аналитика), вход по логину и паролю
- http://localhost:8080/chat — чат на весь экран (ссылка «Чат с консультантом» в шапке витрины и кнопка ⤢ в виджете)

Вместе с приложением поднимается Postgres (сервис `db`) — в нём сотрудники кабинета и их сессии.
При первом запуске создаётся администратор из `.env` (`cp .env.example .env`, впишите `ADMIN_PASSWORD`).
Если пароль не задан, сервер придумает его и напишет в лог: `docker compose logs app | grep администратор`.
Остальных сотрудников администратор добавляет в кабинете → «Сотрудники».

### Учётные записи (локальный Docker)

Сотрудники, которые сейчас заведены в локальной базе (`docker compose`, http://localhost:8080/operator):

| Логин | Пароль | Имя | Роль |
| --- | --- | --- | --- |
| `admin` | `HMn5vPaZnYu5bMmJ` | Анна К. | Администратор — управляет сотрудниками |
| `olga` | `test-pass-123` | Ольга С. | Менеджер — обращения и КП |

> ⚠️ Репозиторий публичный: эти пароли видны всем. Они работают только на локальной машине —
> на Railway своя база и свой администратор. Не используйте их на Railway и в других местах.
> После `docker compose down -v` база создаётся заново: `admin` получит пароль из `ADMIN_PASSWORD` в `.env`, `olga` пропадёт.

Всё хранится в Postgres (том `db_data`) и переживает перезапуск: сотрудники, обращения, сообщения чатов, КП.
При первом запуске с пустой базой создаются 8 демо-обращений из реальных переписок.
Остановить: `docker compose down` (данные останутся), начать с чистого листа (и заново создать администратора): `docker compose down -v`.

### Режим разработки

```bash
docker compose --profile dev up
```

http://localhost:5173 — правки во `frontend/src` применяются сразу. Сервер на Go (:8000) после правок в `backend/`
перезапускается командой `docker compose --profile dev restart api-dev`.

### Пересобрать каталог из нового фида

Положите `Mindbox.yml.gz.xml` и папку `чаты поддержки` сюда, затем:

```bash
docker compose --profile tools run --rm catalog
docker compose up --build app
```

## Деплой на Railway (автодеплой из `main`)

Схема: в проекте Railway два сервиса — **приложение** (собирается из этого репозитория по `Dockerfile`)
и **Postgres** — в нём все данные: сотрудники, обращения, сообщения чатов, КП.

### База данных

| Таблица | Что в ней |
| --- | --- |
| `users`, `sessions` | сотрудники кабинета и их сессии входа |
| `tickets` | обращения: номер, статус, клиент, менеджер, даты + полная запись в `data` (требования, варианты, резюме ИИ) |
| `messages` | сообщения чатов по порядку: обращение, отправитель, текст, время + `data` (карточки, кнопки, оценка) |
| `quotes` | КП: номер, обращение, статус, компания, email + `data` (позиции, условия) |
| `counters` | номера следующего обращения и КП |

Посмотреть данные: в Railway сервис Postgres → **Data** (таблицы прямо в браузере), локально —
`docker compose exec db psql -U app -d support`.

### Первый деплой

1. **Приложение из GitHub.** railway.com → **New Project → Deploy from GitHub repo** → репозиторий.
   Railway найдёт `railway.json` и соберёт `Dockerfile`. Ветка автодеплоя — `main` (сервис → Settings → Source).
   Если проект лежит в подпапке репозитория — там же укажите **Root Directory**.
2. **Postgres:** на холсте проекта **+ Create → Database → PostgreSQL**. Появится сервис `Postgres`.
3. **Переменные приложения:** сервис приложения → **Variables → New Variable**:

   | Переменная | Значение |
   | --- | --- |
   | `DATABASE_URL` | `${{Postgres.DATABASE_URL}}` — ссылка на переменную сервиса Postgres (если сервис назван иначе — подставьте его имя) |
   | `ADMIN_PASSWORD` | длинный пароль первого администратора, **не** тот, что для локального Docker |
   | `ADMIN_LOGIN` | необязательно, по умолчанию `admin` |
   | `ADMIN_NAME` | необязательно: имя, которое клиент увидит в чате, например `Анна К.` |
   | `ALLOW_RESET` | необязательно: `true` — кнопка «Сбросить демо-данные» в кабинете |

   Нажмите **Deploy** (или **Apply changes**), чтобы перезапустить сервис с новыми переменными.
4. **Публичный адрес:** Settings → Networking → **Generate Domain**. Порт сервер берёт из `PORT`, который задаёт Railway.

### Проверка

- **Deployments → View logs**: строки `каталог загружен`, `создан администратор`, `сервер запущен`.
  Если `ADMIN_PASSWORD` не задан, пароль администратора будет здесь же (`создан администратор со случайным паролем`).
- `https://<ваш-домен>/healthz` отвечает `{"ok":true}`.
- `https://<ваш-домен>/operator` → вход под `ADMIN_LOGIN` / `ADMIN_PASSWORD` → «Сотрудники» → добавьте менеджеров.

**Перенос со старой версии.** Если у сервиса остался том `/data` с файлом `db.json` (так хранила обращения прежняя версия),
при первом запуске с пустой базой сервер перенесёт из него обращения, сообщения и КП в Postgres и удалит файл —
в логах будет `обращения перенесены из файла в базу`. После этого том больше не нужен: сервис приложения →
**Settings → Volumes** → удалить.

Администратор создаётся один раз — при первом запуске с пустой базой. Потом `ADMIN_PASSWORD` можно удалить из переменных:
пароль меняется в кабинете → «Профиль». Каждый пуш в `main` пересобирает и перезапускает сервис (2–3 минуты);
если новая версия не стартует, Railway оставляет работать предыдущую.

### Если что-то не так

| Симптом в логах | Что сделать |
| --- | --- |
| `не задан DATABASE_URL` | шаг 3: добавьте `DATABASE_URL=${{Postgres.DATABASE_URL}}` и перезапустите |
| `Postgres недоступен` | проверьте, что сервис Postgres запущен и имя в `${{…}}` совпадает с именем сервиса |
| в кабинете «Неверный логин или пароль» | администратор уже был создан раньше с другим паролем: войдите со старым или удалите в Postgres таблицы `users` и `sessions` (Data → таблица → Delete) и перезапустите приложение |

### Переменные окружения

| Переменная | По умолчанию | Что делает |
| --- | --- | --- |
| `PORT` | `8080` | порт сервера (Railway задаёт сам) |
| `DATA_DIR` | `/data` | только для переноса со старой версии: где искать `db.json` |
| `CATALOG_FILE` / `CHATS_FILE` | `data/catalog.json.gz` / `data/chats.json` | каталог и выжимка из переписок |
| `DATABASE_URL` | — (обязательно) | Postgres: все данные. В docker compose задан сам |
| `ADMIN_LOGIN` / `ADMIN_NAME` | `admin` / `Администратор` | первый администратор (создаётся, пока в базе нет сотрудников) |
| `ADMIN_PASSWORD` | случайный, в логе | его пароль, от 8 символов |
| `POSTGRES_PASSWORD` | `app` | пароль Postgres в docker compose |
| `ALLOW_RESET` | `false` | `true` — включить кнопку «Сбросить демо-данные» в кабинете (иначе кнопки нет, а `/api/admin/reset` отвечает 403) |
| `LOG_REQUESTS` | `false` | писать в лог каждый HTTP-запрос |
| `APP_PORT` / `DEV_PORT` | `8080` / `5173` | порты в docker compose |

## Без Docker

Нужны Go 1.23+, Node 20 (для фронтенда) и Postgres, например `docker compose up -d db`:

```bash
cd backend && DATABASE_URL=postgres://app:app@localhost:5432/support PORT=8000 go run .   # API на :8000
cd frontend && npm install && npm run dev     # http://localhost:5173, /api → :8000
```


## Ограничения демо

- Агент работает на правилах поверх каталога, без языковой модели. Модель подключается в `backend/internal/agent/bot.go`
  (функция `GenerateReply`), фронтенд менять не нужно.
- Сотрудники — в Postgres: роли «Администратор» (управляет сотрудниками) и «Менеджер». Пароли хранятся как scrypt-хеши,
  сессии — случайный токен в HttpOnly-cookie на 7 дней (в базе только его хеш). Выход, смена пароля и отключение
  сотрудника сразу закрывают его сессии. 10 попыток входа за 15 минут с одного IP.
  API менеджера (`/api/tickets`, `/api/quotes`, `/api/stats`, `/api/users`, `/api/admin`) без входа отвечает 401,
  события WebSocket клиент получает только по своему обращению. Имя менеджера в чате и КП берётся из его учётной записи.
  Сброс демо-данных по умолчанию выключен.
- Клиент не входит в систему: его диалог привязан к номеру обращения в браузере.
- Изменения обращений сервер выполняет по очереди внутри одного процесса — рассчитано на один экземпляр сервера.

Подробнее о фронтенде, данных и контракте API — в [frontend/README.md](frontend/README.md).
